# Спайк: разбор структуры таблиц на сканах (oar-ocr), 2026-11-08

Спайк одноразовый, код в репозиторий plaindoc не попал. Рабочая папка (локальная, вне репозитория):
`$SCRATCH/table-spike`
(`src/main.rs` — испытательная программа, `rows.py` и `html2md.py` — разбор вывода, `out/final/` — итоговые таблицы в markdown и HTML,
`out/runs-summary.txt` — сводка всех прогонов, `in/` — входные PNG). Каталоги `target/`, `models/` и `src_dl/` удалены.

Машина: Apple M5 Max, 18 ядер, 48 ГБ. Только процессор (CPU EP), сборка в режиме release.

## Вердикт

**Частично.** Структурная модель на Rust работает, собирается без Python и сочетается с нашим `ort`. Но готовый конвейер oar-ocr на реальном
счёте даёт сетку, которую нельзя сразу использовать.

- **Синтетика** (чистые таблицы с линейками и без): почти идеально. Есть одна системная ошибка: строка «Итого» склеивается с предыдущей строкой.
- **Скан счёт-фактуры** (основной образец): таблица найдена, поворот на 90° исправлен. Сетка неверна:
  - разметка страницы склеивает две таблицы (блок «реквизиты» и блок «товары») в одну сетку 26×16;
  - в блоке реквизитов значения сдвинуты на строку примерно в половине пар;
  - в блоке товаров двухстрочные ячейки распадаются на две строки, а значения смещаются по столбцам.
- **Главная находка для каскада.** Детектор ячеек RT-DETR-L (wired) нашёл на вырезке блока товаров **ровно 40 ячеек из 40 (4×10)**, с ровными
  границами столбцов. Портить результат начинает сшивка oar-ocr «модель структуры + ячейки + OCR», а не зрение.

Рекомендация: каскад делать, но не брать конвейер oar-ocr целиком. Подробности в конце.

Полный набор занимает ~800 МБ. Рабочий минимум (см. ниже) — **~150 МБ**: разметка, det, rec, SLANet+, doc_ori.

PP-OCRv6 tiny по умолчанию в oar-ocr не годится: его словарь (6904 знака) рассчитан на китайский и латиницу. Поэтому OCR заменён на кириллическую
модель PP-OCRv5. Это то же семейство, что у plaindoc-ocr. Файлы ONNX у oar другие: экспорт свой, SHA-256 не совпадает с нашими.

Варианты конвейера (переключались переменными окружения):

| Вариант | Что делает | Итог на счёте |
|---|---|---|
| по умолчанию (как PP-StructureV3) | классификатор типа → SLANeXt + RT-DETR-ячейки + сшивка | мусор: тексты дробятся по кускам, сетка 25×12 |
| сквозной режим для таблиц с линейками (`use_e2e_wired_table_rec`) | SLANeXt без детектора ячеек | реквизиты почти читаемы, блок товаров — мусор |
| «ячейки → HTML» (`cells_trans_to_html`) | сетка из найденных ячеек | 49×13, сплошные rowspan, мусор |
| **без классификатора (всё через SLANet+, сквозной режим)** | — | **лучший результат**, разбирается ниже |
| то же, но без SLANeXt и RT-DETR (минимум) | — | **байт в байт** совпадает с предыдущим |

Классификатор типа таблицы ошибается даже на чистой синтетике: таблицу с линейками он счёл «без линеек» (0.50). Обработка SLANeXt_wired в
oar-ocr 0.10.2 на широких таблицах выдаёт рамки ячеек, «прилипшие» к нижнему краю таблицы (y_max у всех ячеек равен низу таблицы). Поэтому
текст сваливается в первую строку. Это похоже на ошибку разбора выхода модели, а не на слабость самой модели. Подставить SLANet+ в слот для
таблиц с линейками нельзя: падает с ошибкой «structure recognition produced no cells».

### Счёт-фактура: структура (значения замаскированы)

Истина по картинке:

- **таблица реквизитов**, 19 строк × 3 столбца: подпись | код вида «(1а)» | значение. Последняя строка — «Дополнения/условия оплаты» с номером договора.
- **таблица товаров**, 4 строки × 10 столбцов: шапка, 2 позиции, «Итого». Столбцы: наименование, единица, количество, цена, стоимость без
  налога, акциз, ставка НДС (вертикальная надпись), сумма НДС, стоимость с НДС, страна.

Блок реквизитов, лучший вариант (вырезка, SLANet+), фрагмент:

| строка | подпись | код | значение |
|---|---|---|---|
| 0 | Поставщик / Адрес | (1) | ‹заголовок счёта› |
| 1 | | | ‹наименование поставщика› |
| 2 | Получатель | (1a) | — |
| 3 | Счет получателя | (1B) | ‹банк получателя› |
| 4 | Банк получателя | | ‹почтовый адрес› |
| 5 | Кор. Счет | | ‹20 цифр› |
| … | … | … | … |
| 17 | Адрес | | ‹ФИО› |
| 18 | Телефон | | ‹+7…› |
| 20 | Дополния/условия оплаты по договору(контракту) | | Договор №‹…› |

Подсчёт по картинке:

- **Код → значение.** Восемь кодов (1)…(1з) стоят в одной строке со своим значением. Совпало **1 из 8**, остальные сдвинуты на строку вниз.
- **Подпись → значение.** Однозначных пар 14, совпало **~8 из 14**. Часть совпала «случайно»: подпись и значение сдвинулись одинаково.
- **Потеряна целиком** строка «УНП» с назначением платежа и расчётным счётом. Она на сером фоне. Её текст OCR нашёл только в прогоне на повёрнутой
  странице без исправления ориентации.

Блок товаров (вырезка, SLANet+):

- каждая позиция из двух строк текста распалась на две строки сетки;
- единица измерения прилипла к наименованию;
- количество, цена и стоимость без налога первой позиции на месте;
- у второй позиции стоимость уехала на столбец вправо;
- столбцы «стоимость с НДС» и «страна» перемешаны.

Итого ~40 % ячеек на своём месте.

Детектор ячеек RT-DETR-L на той же вырезке нашёл 40 рамок, по 10 в каждой из 4 строк. Границы столбцов совпадают от строки к строке с точностью
до 2–3 пикселей (например 52–887, 886–995, 993–1103 …). То есть правильная сетка 4×10 из него получается.

Полная страница: разметка выдаёт одну область «table» на оба блока. Плюс отдельно «seal» (печать), «header» и «footer».

|---|---|---|---|---|---|

| 2 | Картридж лазерный | шт | 2 | 4 200,00 | 8 400,00 |

Rowspan/colspan в шапке восстановлены верно. Ошибка: сумма «Итого» приклеена к строке 3, а «Итого» растянуто на все 6 столбцов. В счетах строка
итогов есть всегда, так что это существенный риск. Таблица без линеек (6×5) восстановлена полностью. Таблица «подпись → значение» 4×2 в лучшем
варианте восстановлена полностью.

### Качество русского OCR в ячейках

Модель та же, что у plaindoc-ocr (PP-OCRv5 cyrillic), поэтому качество OCR сопоставимо с нашим. Встречено:

- «1» прочитано как «г»;
- ноль как буква: «ООО» → «000», «0» → «о»;
- латиница вместо кириллицы: «ИHH», «5ИK» вместо «БИК», «cyт», «AО»;
- «РБ» → «P5»;
- слипание слов: «г.‹город›ул.‹улица›9» (адрес замаскирован).

Вертикальная надпись «Ставка НДС» потеряна. Латинские двойники лечит наш `fix.rs` в plaindoc-ocr. У oar-ocr такой правки нет.

### Наклон, ориентация, печать и подпись

- **Поворот на 90°**: классификатор ориентации определил 90°, результат совпал с вручную повёрнутой страницей.
- **Небольшой наклон** (около 1° на самом скане и 2° на синтетике) на результат не повлиял.
- **Выпрямление UVDoc ухудшает результат**: на счёте 75 ячеек вместо 123 и меньше распознанного текста, на синтетике потеряна строка «Итого».
  Не включать.
- **Печать** лежит вне таблицы. Разметка выделила её отдельным классом «seal», в таблицу она не попала.
- **Подпись** заходит на строку «Итого» и портит её ячейки: «0» превращается в «oX»/«ox». Строку итогов это и так задевает.

## Риски встраивания в plaindoc

1. **Версия ort совпадает**: оба крейта жёстко закреплены на `=2.0.0-rc.13`. Обратная сторона: обновить `ort` в plaindoc получится только вместе
   с oar-ocr.
2. **Признаки ort.** По умолчанию oar-ocr через `download-binaries` включает `ort/tls-native`, а с ним native-tls и, на Linux, openssl-sys.
   Проверено `cargo tree -i openssl-sys --target all`: цепочка oar-ocr → ort/tls-native → ureq → native-tls → openssl-sys. С
   `default-features = false` и нашим набором признаков ort (`std, download-binaries, tls-rustls, api-27`) проект собирается и работает, openssl
   не тянется. Бинарник со статической ORT весит 38 МБ.
3. **Сборка без Python**: да, только cargo. Но oar-ocr-core безусловно тянет tokenizers (нужен ему для формул), а через него — **onig_sys**:
   библиотеку на C, которую собирает cc. Ещё тянутся nalgebra, imageproc, clipper2, zip, rayon. Всего ~284 крейта против нашего узкого набора.
   Дубли версий: base64, darling, getrandom, itertools, nom, rand, syn 2/3.
4. **Модели OCR дублируются**: у oar свои ONNX-файлы PP-OCRv5 с другими SHA-256. При встраивании OCR нужно брать из plaindoc-ocr, а у oar
   использовать только структурное звено.
5. **Память.** Полный конвейер oar держит 2–5 ГБ на процесс. Для долгоживущего сервиса это много. Если запускать только структурную модель на
   вырезках, это 0.2–0.6 ГБ.
6. **Зрелость.** Крейт активно меняется: 0.10.x, 60 тыс. строк. Найдены ошибки в обработке SLANeXt и в сборке сетки из ячеек, классификатор типа
   ненадёжен.

## Трудоёмкость и рекомендация

Объём кода в oar-ocr, относящегося к таблицам:

- `slanet.rs`: 345 строк;
- `table_structure_decode.rs`: 1045 строк;
- адаптеры и предсказатели: ~1300 строк;
- `table_analyzer.rs`: 1299 строк;
- `stitching.rs`: 2395 строк.

Весь крейт — ~60 тыс. строк.

Рекомендация:

1. **Не подключать oar-ocr целиком.** Получим лишние 2–3 ГБ памяти, onig/tokenizers и ошибочную сшивку.
2. **Каскад для таблиц с линейками (основной случай у госов и банков).** Работает так:
   - дешёвая эвристика находит прямоугольник таблицы и, по возможности, отдельные блоки по горизонтальным и вертикальным линиям;
   - на вырезке запускается RT-DETR-L wired cell det (123 МБ, ~110 мс);
   - сетка собирается своим кодом: кластеризация краёв ячеек по x и y, из этого rowspan/colspan;
   - текст берётся из уже существующего OCR plaindoc по пересечению рамок.

   Оценка: 2–3 дня, ~600–900 строк, порт препроцессинга RT-DETR из oar-ocr (Apache-2.0, с указанием авторства). Альтернатива без модели — чистая
   морфология линий. На этом счёте она, вероятно, справится не хуже, потому что все линейки видны. Её стоит проверить первой как эвристику
   каскада.
3. **Для таблиц без линеек** портировать SLANet+ (7.4 МБ, 25 мс, 178 МБ): модель, декодер токенов и рамок. Это ~1.5 тыс. строк, 3–4 дня. Она
   хорошо работает на чистых таблицах без линеек, а на сканах с линейками хуже детектора ячеек.
4. **Нерешённые вопросы**:
   - строка «Итого» и многострочные ячейки — нужны правила склейки строк;
   - разделение склеенных таблиц;
   - строка на сером фоне выпадает из OCR — это проблема обнаружения текста, к таблицам отношения не имеет;
   - защита от подписи поверх ячеек.
5. **Разметку PP-DocLayoutV3** (124 МБ, 0.2 с, основная доля памяти) в каскад не брать. Таблицы она находит хорошо, но разделить их не может,
   а находить область можно эвристикой.

Итог: идея каскада «эвристика → модель точечно» подтверждается. Модели лёгкие и быстрые на вырезках, а Rust-стек ort rc.13 совместим. Готовой
сшивки «ячейки + текст» в виде, пригодном для счетов, на Rust нет. Её придётся писать самим, и основная работа именно в ней.
