## Отложено: после SP9 (в работу не берём без просьбы)

- **Замеры GPU/CUDA** (нужно железо пользователя; по умолчанию CPU).
- **Финальный проход по производительности:** метрики по типам документов, узкие места, аллокации, ARM/SIMD, unsafe/asm допустимы за проверкой побайтового вывода; сюда же пакетная обработка строк распознавания (batching rec, оценка +10–25 %), int8-квантование, перебор DPI, профиль det/rec, объяснение 2,2 против 0,4 CPU-с на страницу, каскад «дешёвая проверка текста перед полным OCR».
- **Бенчмарк качества против Docling:** судья первым, потом корпуса, таблица «формат / мы / Docling».
- **Модель разметки как необязательный режим точности (S6):** Heron или PP-DocLayout-M для заголовков и списков; только флагом, в каскад не входит.
- **OCR картинок внутри документов** (необязательный режим для картинок с большой долей текста; для схем с блоками смысла не даёт).
- **Подготовка к публикации:** форк `pdf_oxide` как git-зависимость или crates.io, имена в реестрах, README с бенчмарком, реальные документы от пользователя.
- **Сервис в отдельном репозитории** (очередь, HTTP/gRPC, прогретые модели). Библиотеку проектируем под него: лимиты и ошибки без паник, внешняя отмена и таймаут, метрики стадий и пик памяти, детерминизм при параллели.
- **Совместимость с docling-serve** (`DoclingDocument` JSON): только по явной просьбе.
- **WASM во фронте**: идея, не в работе.
- **Хвосты SP8:** пять открытых случаев форка для слоёв OCG (`/D /AS`, группы вне `/OCGs`, глубина `/VE`, нетипизированные OCMD, `/OC` у форм в рендере); ссылки под скрытыми слоями; дедупликация OCR в `ocr_stage` читает текст без фильтра; повёрнутый текст для ссылок; правило `overlap` остаётся только в режиме пометки; **h27** (поддельный слой над сканом в `--ocr auto` не ловится, флаг `--verify-text-layer` только по запросу). Безопасность скрытого текста не приоритет: потребитель работает в песочнице.
- **Хвосты колонтитулов (ruling В-2):** маска цифр считает «Приложение 1» и «Приложение 2» одной нумерованной строкой; `propagate` без охраны `MAX_CANDIDATES`.
- **Хвосты списков PDF (SP8b S1):** два разбора маркеров — `headings::list_marker` (разрывы абзацев 3b) и `list_marker::marker` (списки); они расходятся (`•Text` без пробела, римские `(i)`), свести в один; повёрнутые страницы (`/Rotate`) для векторных маркеров не проверены; оглавление с номерами 1..n становится нумерованным списком; второе чтение путей страницы для векторных маркеров (переиспользовать пути детектора таблиц). Остаточное В3: нумерованные заголовки разделов, у которых тело набрано с висячим отступом (все строки правее номера), становятся нумерованным списком с телом внутри пунктов; однострочный абзац с красной строкой на x текста пункта присоединяется к пункту. Чтение путей из форм XObject не ограничено пределом по байтам.
- **Оценочный набор форм:** в измеренных корпусах нет реальных форм (стопка таблиц ключ—значение, реквизиты); защита `uncertain_page_columns` проверена на форме только синтетически, а на резюме проходит условие «проза» с запасом 2 слова. Нужен реальный образец от пользователя.
- **Мелкие улучшения интерфейса:** явное предупреждение «нужен OCR, но моделей нет» вместо пустого результата; `--page-separator` и метки `<!-- image -->`; очистка устаревших файлов в `<имя>.assets` при повторном запуске; удаление старых кэшей форка (~33 ГБ); кэш моделей сборки: каталог кэша ОС (~/Library/Caches/plaindoc/models, $XDG_CACHE_HOME) вместо каталога данных пользователя.

## Отложено: таблицы без явных линий отдельным режимом (2026-11-08)
Идея владельца: флаг `--borderless-tables`, по умолчанию выключен: таблицы выдаются только при явных линиях/заливках, текстовые (по выравниванию) остаются абзацами. В PDF и DOCX (таблицы с `tblBorders none`, layout-таблицы договоров «Место/Дата заключения») мы рисуем таблицы там, где в документе они не видны. Решено не делать: для LLM текущий вывод приемлем. Правило «границ нет» в DOCX: эффективные `tblBorders` (с учётом стиля и `tcBorders`), заливка ячеек считается видимой структурой.

## Отложено: структура таблиц и ориентация на сканах (спайк 2026-11-08)
Отчёт: [docs/spikes/table-structure-on-scans.md](spikes/table-structure-on-scans.md). Поводом был скан счёт-фактуры (страница повёрнута на 90°): plaindoc и Vision RecognizeDocumentsRequest дали 0 таблиц, Docling одну «таблицу» из одной ячейки.
- Ориентация страницы-скана (0/90/180/270) сделана: голосование по направлению чтения вертикальных строк и проба 180° только на неуверенных страницах, без новых моделей; прямые страницы читаются как раньше. Выпрямление UVDoc ухудшало результат, наклон 1–2° не влияет.
- oar-ocr (Apache-2.0, ort `=2.0.0-rc.13` совпадает с нашим) целиком не подключать: тянет ~284 крейтов, tokenizers/onig, 2–5 ГБ памяти; конвейер склеивает две таблицы счёта в одну сетку. Ячейки RT-DETR-L на вырезке находятся точно (40 из 40, ~110 мс, 580 МБ).
- План каскада: (1) линованные таблицы: эвристика по линиям делит блоки, RT-DETR-L на вырезке, сетку и сшивку с нашим OCR делаем сами (2–3 дня, 600–900 строк; сначала проверить чистую морфологию линий без модели); (2) таблицы без линий: порт SLANet+ (7,4 МБ, 25 мс; 3–4 дня, ~1,5 тыс. строк); (3) PP-DocLayoutV3 в каскад не брать.
- Известные риски: строка «Итого» приклеивается к предыдущей, подпись поверх ячеек, серый фон строки, «0»→«о», «РБ»→«P5».

## Известные пределы ориентации сканов
- Прямая таблица с двумя вертикальными шапками по 40+ знаков без пробелов повернётся (порог `BODY_CHARS`); перевёрнутая на 180° таблица с вертикальными шапками не проверялась.
- Повёрнутая страница, где нет строк в 40+ знаков и есть 3 широких горизонтальных бокса (колонтитул, штамп), читаемых при 0°, не поворачивается (безопасный отказ, как до каскада).
- Нет граничных тестов 39/40 знаков и 2/3 боксов.

## Отложено: оценка на реальном корпусе документов (ждём доступа)
Ожидается доступ к большому корпусу реальных документов пользователей сервиса (порядка 10^5 файлов, уже сконвертированных в Markdown другим инструментом для дистилляции). Корпус и его выводы остаются локально, в репозиторий, отчёты и планы попадают только счётчики и маски. План: (1) описательный проход по всему корпусу (форматы, размеры, число страниц, доля сканов, время, память, паники, пустые результаты); (2) стратифицированная выборка на 300–500 файлов по форматам и типам; (3) сравнение с имеющимся Markdown как с опорным выводом (не эталон истины: разбирать выборку расхождений); (4) пороги настраивать на одной части, проверять на скрытой.

## Известные пределы сборок и OCR
- Linux-сборки требуют glibc 2.38+ и libstdc++ из GCC 13+ (Ubuntu 24.04, Debian 13, Fedora 39, RHEL 10 и новее): так собрана статическая ONNX Runtime из `ort-sys`. На Ubuntu 22.04, Debian 12, RHEL 9 — сборка без OCR (`--no-default-features`), своя ONNX Runtime через `ORT_LIB_LOCATION` или контейнер; подробности в `docs/building.md`.
- Правило пустой страницы (`blank::is_blank`) пропускает OCR на странице, где почти нет краски, одинаково на всех платформах: одно слово кеглем 12 на альбомной странице при 200 dpi лежит на самом пороге (плотность перепадов 0,00036 при пороге 0,0003), и заменяющий Helvetica шрифт (Arial на Windows) переводит его в «пусто». На такой странице `--ocr always` не добавит к текстовому слою ничего нового. Тест `rotated_page_merge_has_no_duplicates` выключает это правило.
